# AGENTS.md

## Описание проекта

- `wdistr` — свой дистрибутив на базе Arch Linux: переупаковка и докрутка
  стока под философию «поставил и работает» (детали и обоснования —
  в разделе «Принятые решения»).
- Репозиторий содержит всё для сборки: `iso/` — профиль archiso (живая
  среда и доставка настроек в целевую систему), `install/` — конфиг
  archinstall и файлы для custom_commands, `vm/` — скрипты виртуальных
  машин (тестовый стенд собранного ISO), `settings/` — перенос настроек
  с хоста. Знания: `Cards/` — компактные собранные знания, на них
  ссылается книга; `handbook/` — книга о проекте, пока в статусе
  черновиков.
- Сборка идёт прямо на рабочей машине — она уже работает под нашим
  дистрибутивом (Arch): `pacman` и `mkarchiso` доступны, репозиторий
  локален. Среда сборки и доустановка пакетов —
  `Cards/Сборочная реальная машина.md`. Прежняя схема (Linux Mint +
  Arch-гость VirtualBox) сохранена историей в
  `Cards/Сборочная виртуальная машина.md`.
- Роли: пользователь принимает решения, агент выполняет работу. Коммиты
  агент делает сам, без отдельного запроса.
- Свои команды — только реально существующие в репозитории: сборка ISO
  `sudo wdistr-build-iso <путь-к-репозиторию>` (детали —
  `Cards/Сборочная реальная машина.md`), проверка собранного образа
  `iso/check-iso.sh [файл.iso]`, перегенерация доставки и конфига
  `python3 install/regen-custom-commands.py`, тестовая VM
  `bash vm/create-test-vm.sh [размер в МиБ]`, рейтинг зеркал
  `python3 rate-mirrors.py [лимит]`. Не выдумывать новых: команда
  появляется по реальной надобности и сразу фиксируется здесь.

## Что требуется

- **VirtualBox 7.2.20** — тестовый стенд собранного ISO
  (`vm/create-test-vm.sh`). Модуль ядра `vboxdrv` собирается из
  `virtualbox-host-dkms` и требует заголовков ядра; доустановка и
  проверка — `Cards/Сборочная реальная машина.md`.
- **Пакеты для сборки**: `archiso` (с зависимостями — `squashfs-tools`,
  `dosfstools`, `mtools`, `libisoburn`, `erofs-utils`), `qemu-img`
  (разбор дисков VM), `linux-headers` (для модуля VirtualBox) — входят
  в базовый набор (`packages[]`, решение 2026-10-12) и на этой машине
  уже стоят; проверка — `Cards/Сборочная реальная машина.md`.
- **Утилиты машины**: `git`, `python3` (перегенерация custom_commands),
  `curl`, `7z`, `tar`, `ssh`, `sshpass` — уже есть (проверено
  2026-10-12).
- **SSH в тестовую VM** — порт 2223, вход по паролю из команды `setup`
  через `sshpass` (решение 2026-10-12: публичный ключ агента больше не
  встраивается в дистрибутив — sshpass покрывает и лайв, и установленную
  систему; ключ `~/.ssh/wdistr_build_vm` остаётся для ручных подключений).
- **Управление консолью VM без SSH** (живая среда, где пустой пароль
  не пускает): ввод команд — `vm/vbox-console.py`, снимок экрана —
  `VBoxManage controlvm ... screenshotpng`; порядок работы и ловушки —
  `Cards/VM - Управление консолью.md`. Агент может сам диагностировать
  и управлять гостем, не привлекая пользователя.

## Принятые решения (2026-09-25)

- Основа — стандартный Arch Linux: переупаковка и докрутка. Своего репозитория пакетов не делаем.
- Направление развития — свои пакеты (решение 2026-10-09, уточнено
  2026-10-12): своего репозитория пакетов НЕ БУДЕТ — свои пакеты идут
  в AUR; когда своих файлов наберётся много, переходить от пофайловой
  доставки к своим PKGBUILD с публикацией в AUR. Сейчас — подручные
  средства: свои настройки и desktop-файлы лежат в `install/files/` и
  доставляются custom_commands (папка `install/files/desktop/` — папка
  под свои .desktop, скрипт `regen-custom-commands.py` доставляет их
  автоматически в `/usr/share/applications`).
- Целевая философия — «поставил и работает» (в духе fish): минимальная настройка, минимализм, без стремления улучшать всё подряд.
- Отношение к Arch — «на самотек», но некоторые компоненты намеренно патчим и замораживаем. Подход должен быть осилим одним человеком + ИИ.
- Оболочка по умолчанию — fish.
- Визуал — тёмная тема в стиле Windows 10. Свой рабочий стол — отдельный проект; его код и конфиги сюда не переносить.
- Направление своего рабочего стола (для отдельного проекта): оконный менеджер без настроек, вшитые тёмные цвета, квадратные окна с контрастной рамкой, панель задач с треем, «Пуск» для выбора программ; цель — стабильность без свистоперделок.
- Временный рабочий стол — Cinnamon (замена xfce4, пробное решение
  2026-10-09: попробовать вместо XFCE, если выбесит — возврат к XFCE
  прост: правка конфига, xfce-настройки в дистрибутиве сохранены);
  дополнительно keyd (раскладки клавиатуры, переключатель раскладки на
  любой клавише). Композитор встроенный в Cinnamon (muffin); picom
  установлен, но не запускается (решение 2026-09-26, см. handbook) —
  picom останется для будущего своего рабочего стола.
- Программы — минимальный базовый набор из репозиториев Arch; расширение охвата через Flatpak; AppImage — только через менеджер обновлений, не обновлять вручную.
- В базовый набор входит `virtualbox-guest-utils` (интеграция мыши/клавиатуры в тестах — решение 2026-09-26) и `virtualbox` (для реальной машины — решение 2026-09-26); состав набора открыт, пополняем по ходу.
- multilib — включить (нужен для steam; решение 2026-09-26). Нюанс: конфиг archinstall multilib включать не умеет — правка pacman.conf живой среды через профиль ISO и установленной системы, задача этапа профиля.
- AUR — разрешён для выбранного списка пакетов, с автообновлением (решение 2026-09-26). Список разрешённых и механизм автообновления — `Cards/Базовый набор программ.md`; реализация — отдельной задачей (помощник ставится из AUR же).
- opencode — в дистрибутив собственной сборки, с патчами (не пакет из extra; решение 2026-09-26). База утверждена 2026-09-27: версия 1, самая последняя = v1.18.32; рецепт сборки — `~/bin/opencode.fish <версия>` (тег + патчи `~/bin/opencode-{1,2,3}.patch` + bun build), при реализации перенести рецепт в репозиторий. Реализация 2026-10-09: рецепт и патчи перенесены в `install/files/opencode/`, доставляются в `~/bin`, первая сборка — на первом запуске (скрипт клонирует репо и собирает от пользователя); версия зафиксирована v1.19.0 (2026-10-12; ветка 2.0 не разбирается), пересборка новой версии — руками `opencode.fish <версия>`. Уточнение 2026-10-13: сборка на первом запуске отключена (бинарник уезжает в ISO готовым, сборка одной и той же версии при каждой установке — лишняя трата времени и места; какая версия будет свежей на момент установки — неизвестна), версия по умолчанию в opencode.fish убрана — только явный аргумент. Направление развития — свой AUR-пакет (см. также «Направление развития — свои пакеты»).
- Идея менеджера «всё в одном» (как в Zorin): общий верхний слой абстракций над установкой программ, пользователь только ставит галочки; источники AppImage — GitHub API, официальные сайты. Пока это идея, не решение: реализацию прорабатывать отдельно.
- Установка — только с собственного ISO (профиль archiso). Собранные ISO и любые эксперименты тестируются в VirtualBox.
- Установка — минимум вопросов: ответы преднастроены, пользователь не отвечает на «1000 дурацких вопросов» (ценность «поставил и работает» распространяется и на установщик; эталон ответов — `handbook/Archinstall - Ответы для нашей системы.md`).
- Установка двухфазная, разметка отобрана у archinstall (решение 2026-10-14): `setup` — фаза 1, офлайн-разметка своими руками (parted, mkfs, сабволюмы @/@home; схема воспроизведена по default_layout); `setup-continue` — фаза 2, закачка и настройка через archinstall в режиме `pre_mounted_config` на смонтированных разделах. Оборвалась сеть — повторяется только `setup-continue`: диск не переразмечается, кэш частично скачанных пакетов (на целевом диске) переиспользуется. Причина: единый archinstall при повторе стирал диск вместе с кэшем (опыт 2026-10-14). Имя `continue` отвергнуто: это builtin sh, перекрывает PATH и падает вне цикла.
- Сборочная среда — решение 2026-10-12: ISO собирается прямо на
  рабочей машине под wdistr, без выделенной VM; доустановка пакетов и
  порядок работы — `Cards/Сборочная реальная машина.md`. Прежняя схема
  (Arch-гость VirtualBox на Linux Mint) отменена, её карточка сохранена
  как историческая — `Cards/Сборочная виртуальная машина.md`.
  Инструменты сборки (`archiso`, `qemu-img`, `linux-headers`) входят в
  базовый набор — дистрибутив собранный умеет пересобрать сам себя.
  Пересоздание тестовой VM (`vm/create-test-vm.sh`) — обычная работа,
  не требует согласования.
- Репозиторий должен стать инструкцией и основой для сборки других вариантов систем: структура профиля и скриптов — обобщённая, не захардкоженная под один дистрибутив (цель варианта Б — полной автоматизации).
- Знания по проекту фиксируются в двух местах (решение 2026-09-25,
  формулировка уточнена 2026-10-08): `Cards/` — компактные собранные
  знания: рабочие инструкции и справки, на них будут ссылаться тексты
  книги; `handbook/` — книга о проекте, пока в статусе черновиков (с
  течением времени — написанные статьи). Вести оба обязательно. Каждая
  столкнутая сложность (что сломалось, в чём причина, как вышли) — статья
  в `handbook/`; перечень таких статей — прямая цель проекта.
- Форматы handbook: статьи-объяснения — как что устроено; нерешённые проблемы — статьи с префиксом `Проблема - ` (симптом, что известно, что пробовали, статус «не решено», непроверенные идеи). Рецепты и команды включать только реально применимые в описанной ситуации.
- Память сессий (`.agents/memory/*.md`) — рабочий склад, не архив
  (привычка 2026-10-15): копление устаревшего даёт когнитивный шум —
  пример: отменённые запреты на зеркала продолжали вылезать из старых
  записей, пока их не вычистили везде разом. За сессию подчищать не
  меньше двух устаревших записей (уточнять или удалять — в зависимости
  от ценности контекста); явно устаревшее (отменённые решения,
  брошенные схемы, содержимое «только что» заменённых файлов) чистить
  сразу по факту, не дожидаясь следующей сессии.
- Часть компонентов намеренно «заморожена» от улучшений: не модернизировать и не переписывать без явного запроса. Список конкретных позиций появится здесь по ходу работы.
- Первый запуск — автоинициализация (решение 2026-09-26): `pacman -Syu` (базы всех репозиториев, включая multilib) + подключение flathub; лог каждого запуска — `~/install-log/first-boot.log` (читаемо пользователем и агентом), туда же планируется AGENTS.md дистрибутива для сценария самопроверки opencode'ом. Список программ из flatpak — отдельно, по списку пользователя (читки новостей не нужны, многое есть в репозиториях Arch).
- Идея (2026-09-26): opencode в дистрибутиве как средство самопроверки — после инициализации открыть папку, запустить opencode, сказать агенту «проверь»: он сам разбирается по AGENTS.md, что проверять. Тогда дистрибутиву нужен свой AGENTS.md с инструкциями проверки.
- Источники программ (решение 2026-10-09): **родной пакет
  (extra/multilib) > AUR > flatpak** (разрешённый список; см.
  `Cards/Базовый набор программ.md`). Прежний порядок (2026-09-27,
  flatpak выше AUR — уточнение 2026-10-08) отменён: песочница прячет
  системные темы — приложения слетают на светлые. В flatpak остаётся
  steam (вопрос vulkan-драйверов в multilib-версии) и программы, пока
  не разобранные поштучно.
- Идея (2026-09-26): тяжёлые и «вопросительные» программы (steam и подобные) ставить через flatpak — там нет интерактивных вопросов вроде выбора vulkan-драйвера.
- Зеркала Arch (решение 2026-10-08; политика уточнена 2026-10-15): по
  умолчанию обе системы работают со списком из `mirrors.txt` (в корне
  репозитория). Доставка разная: живая среда — хук с источником
  `wdistr-mirrors.hook` (нужен при сборке, pacman-mirrorlist там
  свежеустанавливается), устанавливаемая — одноразовая запись
  `/etc/pacman.d/mirrorlist` при установке. **Правки зеркал в
  работающей системе разрешены**: mirrorlist входит в backup-массив
  pacman-mirrorlist — правки переживают обновления пакета (новый сток
  приходит в `.pacnew`), поэтому хук в цель не доставляется. Состав
   выбирается по статистике `rate-mirrors.py` (ноль отказов в истории,
   средняя скорость, одна позиция на страну, потолок оператора — 3);
   **запретов на конкретные зеркала нет — черные списки отменены**
   (решение 2026-10-15): причина прыганий была в приоритете IPv6 над
   IPv4 (строка `precedence` в gai.conf), а не в зеркалах; выбор
   только по свежему замеру. Yandex возвращён в пул кандидатов тем же
   решением (в `mirrors.txt` пока не входит — состав меняется
   отдельным решением). Техническое
  требование: заголовок региона в mirrorlist (сейчас `## wdistr`)
  обязан совпадать с ключом `mirror_regions` в конфиге archinstall —
  заменять заголовок на свой комментарий нельзя, установка упадёт по
  KeyError; детали и что можно —
  `Cards/Зеркала - Статический список и регион wdistr.md`.
- Timeshift (решение 2026-10-13): конфиг `timeshift.json` в дистрибутив
  не поставлять — нужны ли снимки и какие, решает пользователь сам
  (настройка через первый запуск `timeshift-gtk`; конфиг машинозависим —
  в нём UUID диска). Таймер `wdistr-timeshift-check` включён по
  умолчанию: до настройки конфига он пишет `rc!=0` в лог — ожидаемо,
  не поломка (см. `Cards/Расписание - Конфликт таймеров обновлений и
  Timeshift`). Порядок очереди обновлений: `timeshift-check` идёт
  `Before` трёх обновлений — снимок-эталон до `pacman -Syu`, для отката.
- Пока не решено и требует согласования перед реализацией: состав базового набора программ (граница «что входит в ISO, а что ставится потом»; рабочий список — `Cards/Базовый набор программ.md`), реализация multilib и автообновления AUR, выбор менеджера обновлений AppImage, реализация менеджера «всё в одном».
