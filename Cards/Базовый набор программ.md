Служебный состав и рабочий стол — минимум, без чего система не работает;
приложения — предпочтения пользователя.

## Служебный состав

`xorg-server` — X-сервер.
`lightdm` — экран входа.
`lightdm-gtk-greeter` — оформление экрана входа.
`picom` — композитор; не запускается, остаётся для будущего wdesktop.
`virtualbox-guest-utils` — интеграция гостевой VM (мышь, экран).
`virtualbox` — для реальной машины.
`adwaita-cursors` — системный фолбэк курсоров (основной — McMojave, см. чек-лист «Комфортный рабочий стол»).
`papirus-icon-theme` — тема иконок по умолчанию; вносим явно.
`xorg-xsetroot` — установка фона/свойств X.
`xorg-setxkbmap` — смена раскладки из скрипта переключения (keyd).
`pipewire` — звуковой сервер.
`pipewire-pulse` — совместимость с PulseAudio.
`pipewire-alsa` — совместимость с ALSA.
`wireplumber` — сессионный менеджер pipewire.
`pavucontrol` — графический микшер звука.
`blueman` — менеджер Bluetooth; демон `bluez` и `bluez-libs` приезжают зависимостями (в конфиг вносим только blueman). Сервис `bluetooth` включён в `services[]` (2026-10-15): без него GUI на месте, а демон не запущен — blueman молчит.
`gnome-keyring` — хранилище ключей (нужен программе Authenticator).
`udisks2` — монтирование дисков без root по запросу программы.
`xdg-utils` — `xdg-open`: открытие файлов и ссылок (ни firefox, ни thunar его не тянут).
`ttf-dejavu` — базовые шрифты.
`openssh` — доступ по SSH (в живой среде и для целевой системы).
`base-devel` — инструменты сборки (makepkg — нужен для AUR-пакетов).
`git` — клонирование AUR-репозиториев (установка yay) и прочие задачи.
`bun`, `nodejs`, `node-gyp` — JavaScript-стек для сборки opencode
(см. раздел «opencode»); входят в `packages[]` с 2026-10-09, до
переноса рецепта сборки в дистрибутив.
`rsync` — нужен timeshift для rsync-режима снимков; вносим явно, чтобы не зависеть от зависимостей пакета.
`ttf-ubuntu-font-family` — шрифт интерфейса по умолчанию (назначается dconf-дефолтом).
`terminus-font` — консольный шрифт ter-u16n (кириллица в TTY). Раньше файл в целевую попадал только копией из живой среды (setup), в сам `packages[]` не входил — из-за этого `console_font: ter-u16n` в конфиге archinstall не мог примениться до нашей доставки; с пакетом шрифт в целевой появляется сразу после pacstrap. В живой среде пакет стоит отдельной строкой `iso/packages.x86_64`.
`noto-fonts`, `noto-fonts-cjk`, `noto-fonts-emoji`, `noto-fonts-extra` — базовое семейство Noto: текст и интерфейсы (основной пакет), CJK (китайский/японский/корейский — иероглифы в интерфейсах и вебе), эмодзи, расширенные начертания (жирные, моноширинные и пр. для веба).

## Приложения

Программы берём из репозиториев Arch (extra, core, multilib); если нужного
там нет — из AUR; и только если нет ни там, ни там — из flatpak. Прежний
порядок был обратным (flatpak выше AUR), но он не прижился: приложения
в песочнице не видят системных настроек темы и слетают на светлые, а
AUR-пакеты живут в системе и слушают её настройки напрямую. В flatpak
остался только steam — там он приносит свой runtime с драйверами и
ставится без вопросов о vulkan.

Колонка «Установщик» показывает, когда программа попадает в систему.
`конфиг` — сразу при установке дистрибутива, пакет ставится из
`packages[]` конфига archinstall. `скрипт` — на первом запуске уже
установленной системы: автоинициализация ставит AUR- и flatpak-пакеты
из списков в `first-boot.sh`.

**Строка в таблице — это ещё не дистрибутив.** Запись «репозиторий +
конфиг» становится настоящей только после двух действий: пакет добавляется
в `packages[]` файла `install/archinstall-config.json` и прогоняется
`python3 install/regen-custom-commands.py` (иначе конфиг в профиле ISO
останется прежним, и пакет до живой среды не доедет). Уже теряли так
пакеты: zeal и шесть приложений (godot, keepassxc, obsidian, okular,
copyq, qbittorrent) числились в таблице, но в конфиг не попали.
Отдельный проверяющий скрипт для этого не заводим — механика лишняя;
при правке таблицы сверяйтесь с конфигом глазами. Порядок сверки —
`Cards/Состав - Проверка таблицы программ.md`.

Почему steam — flatpak: установка `steam` из
multilib интерактивно спрашивает 32-битный vulkan-драйвер под конкретное
железо (`lib32-vulkan-radeon` для AMD, `lib32-vulkan-intel` для Intel,
свой для NVIDIA) — ровно тот вопрос, который мы хотим убрать.
Flatpak-версия приносит свой runtime с mesa-драйверами и ставится без
единого вопроса. Multilib в дистрибутиве остаётся (wine, 32-битные
мелочи), сам steam — flatpak-путём после подключения flathub (задача
автоинициализации первого запуска).

Почему приоритет на AUR перед flatpak: в песочнице
приложения не видят системных настроек GTK — темы слетают на светлые,
приходится бороться разрешениями и порталами; AUR-пакеты ставятся в
систему, читают темы и иконки напрямую, а у нас уже есть системные
дефолты dconf (Adwaita-dark) и `/etc/gtk-3.0/settings.ini`, которые их
держат тёмными. Издержки AUR (чужой PKGBUILD исполняется при сборке,
сборка требует времени) приняты осознанно: список разрешённых пакетов
закрыт, ставятся только они.

## opencode — собственной сборки

Не пакет из extra, а собственная сборка с патчами. Дистрибутив
**поставляет готовый бинарник**: сборка `opencode-1.19.3` лежит в
живой среде (`iso/airootfs/usr/local/bin/`, симлинк `opencode`) и при
установке копируется в целевую систему. Сборка на первом запуске
отключена (решение 2026-10-13): одна и та же версия при каждой
установке — лишняя трата времени и места (~6 ГиБ `~/src/opencode`).

Пользователь в любой момент может **собрать свежую версию сам** —
прогоном одной команды от своего имени:

```fish
opencode.fish 1.19.1   # версия обязательна, дефолта в скрипте нет
```

Скрипт клонирует репозиторий (`~/src/opencode`, при первом запуске),
переключается на тег, применяет патчи, собирает бинарник и кладёт его
в `~/bin/opencode-<версия>` с обновлением симлинка `~/bin/opencode`.

Что для этого нужно — уже в системе:

- зависимости сборки `bun`, `nodejs` и `node-gyp` — в `packages[]`
  конфига установки (стоят там с 2026-10-09, изначально под сборку
  opencode);
- скрипт `install/files/opencode/opencode.fish` и четыре патча
  `install/files/opencode/opencode-{1,2,3,4}.patch` доставляются в
  `~/bin` первого пользователя (custom_commands) — по паттерну: всё
  своё в одном месте;
- `git` и `base-devel` — в составе дистрибутива.

Патчи авторские, применяются к чистому тегу перед сборкой:

1. убрана автогенерация заголовка сессии (`session/prompt.ts`);
2. дата в системном промпте стабилизирована, чтобы префикс сохранялся
   (`core/src/system-context/builtins.ts`, `session/system.ts`);
3. файлы инструкций стабилизированы на сессию
   (`session/instruction.ts`, `session/prompt.ts`);
4. TUI держит в памяти только хвост транскрипта (окно последних
   сообщений сессии); вытеснение старых сверху включается только когда
   читатель внизу истории — иначе удаление строк сверху сдвигало бы
   видимый текст (`packages/tui/src/context/sync.tsx`,
   `packages/tui/src/routes/session/index.tsx`).

Направление развития — свой AUR-пакет вместо ручной доставки
(когда стабилизируется сборка). Пересборка бинарника в ISO после
смены версии/патчей — вручную, `Cards/Сборочная реальная машина.md`.

## Открытые вопросы

- Граница «что входит в ISO, а что ставится потом» — состав базового
  набора требует согласования перед реализацией (см. AGENTS.md).
