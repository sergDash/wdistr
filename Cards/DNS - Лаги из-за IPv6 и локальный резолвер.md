## Симптом и диагноз (опыт 2026-10-15)

Симптом: периодические лаги, подозрение на сбои DNS. Замеры показали,
что сам резолвер здоров: три домена за 0.23 с, пинг 8.8.8.8 — 46 мс,
`curl -4 https://ya.ru` — 0.3 с. Копание в логи и маршруты дало
настоящую причину — связку из трёх фактов:

1. **IPv6 на проводе мёртв.** На `enp6s0` `disable_ipv6=1`
   (/proc/sys/net/ipv6/conf/enp6s0/), глобального маршрута IPv6 нет,
   пинг по IPv6 наружу — 100% потерь.
2. **VPN-туннель `amn0` (Amnezia) перехватывает весь IPv6.**
   Маршруты `::/1` + `8000::/1` делят адресное пространство пополам и
   покрывают его целиком. Маршрут формально есть, но туннель трафик не
   доставляет — получается чёрная дыра с виду рабочая.
3. **DNS отдаёт AAAA-записи**, и часть резолюций возвращает IPv6-адрес
   приложению (первый же `getent hosts ya.ru` вернул только
   `2a02:6b8::2:242` без IPv4).

Механизм задержки: приложение берёт IPv6-адрес, SYN уходит в маршрут
туннеля и теряется, TCP ждёт до таймаута — `curl -6` провисел все 8
секунд и был отсечён, после чего стек пробует IPv4 и соединение
открывается. Каждый такой эпизод — видимый лаг. То есть ломалось не
разрешение имён, а выбор адреса для соединения после удачной резолюции.

### Лечение: приоритет IPv4 в glibc

```
precedence ::ffff:0:0/96  100
```

Одна строка в `/etc/gai.conf` смещает выбор адреса в glibc в пользу
IPv4. Файл читается заново при каждом вызове резолюции, перезапуск
ничего не требуется. Проверка после правки:

- `getent ahosts ya.ru` — IPv4-адресы идут первыми, IPv6 уходит в конец;
- `curl https://ya.ru` (без флагов) — открывается за ~0.6 с, не упираясь
  в мёртвый маршрут.

Что осталось после лечения: приложениям **со своим кэшем DNS** нужен
перезапуск (браузеры помнят закэшированные раньше адреса). Мёртвый
маршрут `::/1` в туннеле никуда не делся: программы, лезущие по IPv6 в
обход glibc (прямой `AF_INET6`, `curl -6`), по-прежнему виснут до
таймаута. Полная чистка — убрать `::/1` и `8000::/1` из AllowedIPs
конфига Amnezia (опциональный шаг, делать по надобности).

Разовый сбой из диагностики: один AAAA-запрос упал по таймауту на всех
трёх серверах, повторные прогоны (UDP, TCP, 1.1.1.1, 8.8.4.4) прошли.
Не воспроизводится — но указывает, что туннель `amn0` нестабилен по
UDP и периодически пересоздаётся (в логах NetworkManager удаление и
создание видны). Если лаги вернутся — начинать со стабильности туннеля,
а не с резолвера.

## bind: пакет = утилиты + сервер

`pacman -S bind` ставит две независимые части: утилиты `dig`, `host`,
`nslookup` (нужны для диагностики — по ним и опрашивались серверы) и
сам DNS-сервер `named`. Для рабочей станции named не нужен: он
авторитативный сервер с зонами и динамическими обновлениями, задачу
кэша решает лучше и проще локальный кэширующий резолвер. `dig` без
сервера полностью работает.

## Зачем свой DNS-сервер на машине

Каждый запрос сейчас идёт наружу через туннель (8.8.8.8 перехвачен
маршрутом `0.0.0.0/1`), а туннель даёт разовые таймауты и
пересоздаётся. Локальный кэш устраняет зависимость от этого:
повторные имена разрешаются из памяти мгновенно, при обрыве туннеля
недавние ответы продолжают работать. Дополнительно — локальные имена
(контейнеры docker) без правки `/etc/hosts`.

Варианты, отсортированные по нашему выбору:

- **systemd-resolved** — уже установлен в системе: `resolvectl` на
  месте, в `/etc/nsswitch.conf` строка `hosts:` уже содержит
  `resolve [!UNAVAIL=return]`, просто сервис `inactive`, а resolv.conf
  пишет NetworkManager напрямую. Инфраструктура полунаведена.
- **dnsmasq** — лёгкий, кэш + локальные имена, есть плагин для
  NetworkManager (тот поднимает и управляет сам).
- **unbound** — минимальный кэширующий резолвер, ручной конфиг.
- **named (bind)** — только ради его собственного функционала; для
  кэша избыточен.

### Переход на systemd-resolved: порядок

Одного `systemctl enable --now` мало: сейчас у резолюции два владельца
(NM пишет файл, DHCP его перезаписывает). Порядок:

1. `sudo systemctl enable --now systemd-resolved` — поднимает слушающий
   сокет `127.0.0.53:53`, это и есть локальный резолвер с кэшем.
2. Заменить файл симлинком: `sudo ln -sf
   /run/systemd/resolve/stub-resolv.conf /etc/resolv.conf` — штатный
   выход для программ, читающих файл напрямую, минуя NSS.
3. Перевести NetworkManager в режим `dns=systemd-resolved` (в `[main]`
   файла `/etc/NetworkManager/NetworkManager.conf`; часть версий NM
   переключается сам при активном resolved — проверить по факту).
   После этого NM перестаёт перезаписывать resolv.conf и передаёт DNS
   от соединений в resolved по D-Bus.
4. Проверка: `resolvectl status` (видны серверы под интерфейсом),
   `resolvectl statistics` (запросы и попадания в кэш), повторный
   замер скорости.

Опыт отладки на рабочей машине (2026-10-16): NM 1.58 переключается
**сам** — после шагов 1–2 серверы (8.8.8.8, 93.100.1.4, 94.19.255.5)
видны в `resolvectl status` под интерфейсом `enp6s0`, без правки
NetworkManager.conf. Кэш отрабатывает: повторный `resolvectl query` —
3 мс («Data from: cache»), в statistics попадания растут. Контейнер
Docker резолвит (docker0 в resolved без scope — штатно, контейнеры
берут DNS через демон, 127.0.0.53 отфильтровывают сами и уходят на
свои дефолтные серверы; из кэша хоста не кэшируют — изолированы
осознанно). В дистрибутив внесено тем же днём: сервис в `services[]`,
симлинк в custom_commands, проверки в check-iso.

Нюанс: Docker при старте контейнеров берёт DNS из файла хоста;
loopback-адрес `127.0.0.53` он обычно отфильтровывает сам, но сеть
контейнеров после переключения проверить.

Отдельного пакета `systemd-resolved` в Arch больше нет — входит в
состав пакета `systemd` (проверено 2026-10-16, pacman 262-1);
в `packages[]` ничего добавлять не нужно, `resolvectl` на месте.

## Куда вписывать DNS-серверы после перехода

`/etc/resolv.conf` под симлинком перестаёт быть местом настройки —
файл пересоздаёт сам resolved, правки в него исчезают. Настройка
разъезжается по двум местам:

- **NetworkManager — конкретные серверы** (основное место, оно же и
  сейчас): `nmcli con modify "Проводное подключение 1" ipv4.dns
  "8.8.8.8 1.1.1.1"`, при необходимости `ipv4.ignore-auto-dns yes` не
  подмешивать DNS из DHCP; либо графический NM → вкладка IPv4 →
  «DNS-серверы». NM продолжит передавать эти адреса в resolved.
- **`/etc/systemd/resolved.conf` — поведение резолвера**: `DNS=`
  (серверы поверх адресов от NM), `FallbackDNS=` (куда идти, когда всё
  не отвечает), `Domains=` (маршрутизация по доменам), `DNSSEC=`.
- **`resolvectl dns <интерфейс> ...`** — разовые правки для проверки,
  сбрасываются при перезапуске resolved.

Текущий список из трёх серверов (`8.8.8.8`, `93.100.1.4`,
`94.19.255.5`) никуда не денется — он уже в NetworkManager, просто
станет виден в `resolvectl status`.

## Связь с gai.conf

Локальный резолвер не заменяет правку `gai.conf`: порядок выбора
адреса для соединения решает glibc, а не DNS-сервер — AAAA-записи
останутся такими же, просто быстрее будут отдаваться. Обе правки
независимы: сначала gai.conf (лечит лаги), резолвер — для устойчивости
и кэша.
