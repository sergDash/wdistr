Полный проверенный конвейер: от профиля до тестируемого ISO (2026-09-26).

## Где что живёт

- Профиль — `iso/` в репозитории (снят с пакета archiso-90 из extra;
  версию профиля держать синхронизированной с archiso в сборочной VM).
- Сборка — в сборочной VM `wdistr-build` (Arch, пакет `archiso`); её
  создание, подготовка и подключение — `Cards/Сборочная виртуальная
  машина.md`.
- Выходные файлы mkarchiso создаются в `out` **относительно текущей папки
  запуска** (запуск из `~` → `~/out`), не профиля.
- Тестовый стенд — `vm/create-test-vm.sh` (VM `wdistr-test` со свежим
  `iso/out/wdistr-*.iso`).

## Бинарник opencode в ISO (страховка)

В установленной системе всегда должен быть рабочий `opencode` — чтобы
пользователь мог подключиться к ИИ за помощью сразу после установки,
не дожидаясь фоновой сборки на первом запуске. Бинарник кладётся в
профиль **перед сборкой тарбола**:

1. Собрать opencode (рецепт — `~/bin/opencode.fish`, версия по умолчанию
   зафиксирована в скрипте).
2. Скопировать бинарник в профиль:
   `cp ~/bin/opencode-<версия> <репо>/iso/airootfs/usr/local/bin/`
3. Симлинк `opencode -> opencode-<версия>` уже стоит в репозитории
   (крошечный файл, версионируется). При смене версии — обновить его:
   `ln -sf opencode-<новая> iso/airootfs/usr/local/bin/opencode`.

Бинарник (~170 МБ) в git не версионируется — в `.gitignore` есть
`iso/airootfs/usr/local/bin/opencode-*`. Поэтому перед каждой сборкой
ISO его нужно класть заново — он не переживает git pull.

В установленной системе: `/usr/local/bin/opencode` работает сразу.
Фоновая сборка первого запуска позже кладёт свежую версию в
`~/bin/opencode` — она перекрывает системную (`~/bin` в PATH раньше
`/usr/local/bin`). Если сборка упала — системная страховка остаётся.

## Передача профиля в сборочную VM

Хост раздаёт репозиторий: `python3 -m http.server 8000` (из корня
репозитория). В госте:

```sh
curl -fsSL http://10.0.2.2:8000/iso-profile.tgz -o /tmp/p.tgz
tar -xzf /tmp/p.tgz -C ~          # даёт ~/iso; sudo не нужен
```

Тарбол собирается на хосте: `tar czf iso-profile.tgz iso` (файл в
`.gitignore`).

## Сборка

```sh
sudo mkarchiso -v ~/iso            # путь явный, см. handbook/Проблема - mkarchiso не находит профиль.md
```

## Вынос готового ISO на хост

Обратный канал — проброс `isoout` (9999→8000), он прописан в VM при создании
(см. `Cards/Сборочная виртуальная машина.md`). В госте: `cd ~/out && python3 -m
http.server 8000`. На хосте: `curl -o iso/out/<имя>.iso
http://127.0.0.1:9999/<имя>.iso`.

Вместо этого канала можно отдать файл по SSH (порт 2222): `scp -P 2222
-i ~/.ssh/wdistr_build_vm user@127.0.0.1:~/out/<имя>.iso iso/out/`.

## Проверка содержимого ISO без загрузки

```bash
7z x -o/tmp/x <iso> arch/x86_64/airootfs.sfs
unsquashfs -d /tmp/x/ex /tmp/x/arch/x86_64/airootfs.sfs etc/hostname root/wdistr
```

## Тест

```bash
bash vm/create-test-vm.sh          # пересоздание: VBoxManage unregistervm wdistr-test --delete
```

В госте: `sh /root/wdistr/go.sh --dry-run`, затем `sh /root/wdistr/go.sh`.

**Память тестовой VM: 8 ГБ МАЛО** (случай 2026-10-09): первый запуск
(AUR-сборки librepcb, jan, localsend) даёт пик памяти ~6.8 ГБ, и OOM
killer убивает `wdistr-first-boot` (юнит `failed`, повтор при загрузке
помогает двигаться дальше, но бесконечные повторы не заменяют память).
Для теста поднимать до 16 ГБ: `VBoxManage modifyvm wdistr-test --memory
16384` (на выключенной машине). На реальном железе с большой RAM
проблемы нет.

## Известные особенности

- В живой среде нет команды `hostname` — проверять `cat /etc/hostname`.
- В текстовой консоли живой среды мышь захватывается (интеграция неактивна
  до X) — в окно не кликать.
- Для пересборки после правок профиля: заново тарбол → передача → сборка.
  Изменения вида «добавить пакет в живую среду» — `iso/packages.x86_64`;
  изменения содержимого установленной системы — конфиг в `install/`.

## Перед передачей профиля

Если правились файлы в `install/files/` или `mirrors.txt` — пересобрать
команды доставки:

```bash
python3 install/regen-custom-commands.py   # сам синхронизирует конфиг с профилем
```

Иначе изменения не доедут до устанавливаемой системы (airootfs настраивает
только живую среду, целевая система получает настройки через custom_commands).

- Выключение тестовой VM командой `controlvm ... acpipowerbutton` может
  не сработать (2 случая 2026-09-26, XFCE-гость) — тогда `controlvm ... poweroff`
  (данные тестовые, допустимо).

## Перед КАЖДОЙ пересборкой — удалять work и out

Внутри `work/` mkarchiso хранит маркеры «шаг уже выполнен». Если каталог
остался от прошлой (или прерванной) сборки, повторный запуск **молча
пропускает все шаги и завершается с кодом 0, не создав ISO** — выглядит
как мгновенное «падение» после `Validating options... Done!`
(случай 2026-09-26). Безопасный шаблон перед запуском:

```sh
sudo rm -rf /home/user/work /home/user/out
cd /home/user && nohup sudo mkarchiso -v /home/user/iso > /home/user/build.log 2>&1 < /dev/null &
```

Проверка, что сборка реально идёт: в логе через ~10 секунд должны появиться
строки `checking keyring...` / загрузки пакетов, а не только `Done!` валидации.

## Во время сборки на сборочной VM — НЕ запускать pacman

Сборка держит блокировки pacman. Параллельный запуск `pacman -S ...`
(случай 2026-09-26: пользователь ставил htop) ведёт к конкуренции за
`db.lck`: шаг `Updating linux initcpios` падает с
`Pacman is already running ... lock never exited`, initramfs не создаётся —
и сборка доходит до конца, выдав **битый ISO** с ошибкой
`install: cannot stat '.../initramfs-*.img'`.

Правило: пока идёт mkarchiso, на сборочной машине ничего не ставим.
Всё докачиваем после (в том числе htop и прочие личные утилиты).
При таком отказе — чистка `work/`+`out/` и полная пересборка.
- Имена файлов в `iso/airootfs/usr/local/bin/` не должны совпадать с
  coreutils (`install` сломал две сборки — см.
  `handbook/Проблема - Имя install ломает сборку ISO.md`; команда
  переименована в `setup`).
