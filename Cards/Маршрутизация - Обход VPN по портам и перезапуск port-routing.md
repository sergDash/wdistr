## Как устроен обход VPN по портам

Два systemd-сервиса:

- **ip-routing.service** — хостовые маршруты напрямую через `enp6s0`
  (`62.113.107.38`, `130.17.16.223`, `172.65.90.20–23` — opencode.ai).
- **port-routing.service** — две вещи:
  1. `ip route replace default via 192.168.0.1 dev enp6s0 table port`
     («всё напрямую»);
  2. `ip rule add sport NNN table port` для портов 80, 443, 25, 587, 993,
     143, 9987, **25565**, 37860, 28015, 16261–16264.

Идея: когда пакет **выходит** с исходным портом из списка (`sport`), ядро
смотрит в таблицу `port` и шлёт его напрямую через `enp6s0`, мимо туннеля.

Важно: `ip rule` проверяет **исходный** порт (`sport`), а не порт назначения.
Для сервера (Minecraft, 25565) это ответные пакеты: у ответа исходный порт
25565 → правило срабатывает → таблица `port` → напрямую.

## Симптом

`ip rule show` показывает `32758: from all sport 25565 lookup port`, но

```
ip route show table port     # пусто
ip route get 1.1.1.1 sport 25565
→ 1.1.1.1 dev amn0 src 10.8.1.2   # уходит в VPN, хотя не должен
```

## Причина

`port-routing.service` отрабатывает **один раз** при загрузке (Type=oneshot,
RemainAfterExit=yes). Стартует → кладёт маршрут в таблицу `port` → дальше живёт
своей жизнью. Но:

- При событиях `amn0 up/down` (перезапуск Amnezia) и `enp6s0 up` (моргание
  кабеля) ядро вычищает маршруты через исчезнувший интерфейс — в том числе
  `default ... table port`.
- Диспетчер `90-ip-routing-restart` на эти события перезапускает **только
  `ip-routing.service`**. `port-routing.service` он не трогает.

Итог: host-маршруты ip-routing восстанавливаются, а маршрут в таблице `port`
— нет. Правила `ip rule` остаются (они не маршруты и не чистятся), но
указывают в пустую таблицу. Ядро не находит маршрут в `port`, проваливается
ниже → `main` → `0.0.0.0/1` и `128.0.0.0/1` → `amn0`. Bypass молча
перестаёт работать для всех перечисленных портов.

## Исправление

В `/etc/NetworkManager/dispatcher.d/90-ip-routing-restart` на тех же
событиях (`enp6s0 up`, `amn0 up`, `amn0 down`) добавить перезапуск
`port-routing.service` — так же, как сейчас сделано для `ip-routing`:

```bash
systemctl --no-block restart port-routing.service
```

Перезапуск на `amn0 down` безопасен: `ExecStartPre` порт-сервиса ждёт
появления адреса на `enp6s0`, а `enp6s0` от `amn0` не зависит. На событие
`enp6s0 down` не реагируем — так же, как в текущем диспетеchере для
ip-routing: маршрутов уже нет, а wait-цикл ждал бы адреса и блокировал NM.

## Проверка после правки

```bash
# перезапустить VPN или кабель, затем:
ip route show table port          # должен быть default via 192.168.0.1 dev enp6s0
ip route get 1.1.1.1 sport 25565  # должен быть dev enp6s0, не amn0
```

## Замечания

- Имя таблицы `port` резолвится через `/etc/iproute2/rt_tables`; на Arch
  каталога может не быть — сервис сам создаёт его и дописывает строку
  `100 port` (опыт 2026-10-14, зафиксирован в ExecStartPre юнита).
- Имя `port` выбирается, чтобы не совпадать с числом: числовые id таблиц
  конфликтуют с приоритетами правил.
