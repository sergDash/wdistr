summary:
  Как wdistr включает user-сервисы (пример — демон syncthing): ручной
  симлинк в default.target.wants через custom_commands, почему в chroot
  не работает systemctl --user, когда сервис оживает; способы для
  нескольких и будущих пользователей — профили archinstall и /etc/skel.
date: 2026-10-09

Включённый при установке пример — демон `syncthing` (решение
2026-10-09): синхронизация — пользовательская задача (конфиг лежит в
домашнем каталоге, файлы — пользовательские), поэтому сервис
пользовательский, а не системный.

**Как включается.** В `install/regen-custom-commands.py` есть команда
`custom_commands`, которая от root в целевой системе:

1. находит первого обычного пользователя (`$U` — uid 1000–65534, имя
   из setup не захардкожено);
2. создаёт `~/.config/systemd/user/default.target.wants/`;
3. кладёт туда симлинк на `/usr/lib/systemd/user/syncthing.service`
   (файл из пакета);
4. делает `chown` домашнего каталога пользователю.

**Почему симлинк, а не `systemctl --user enable`.** Команды установки
выполняются в chroot целевой системы: пакеты уже распакованы, но
user-менеджер ещё не запускался и user-шины не существует —
`systemctl --user` в таких условиях падает с ошибкой подключения.
Симлинк — ровно то, что `enable` создаёт под капотом; цель
пользовательских юнитов по умолчанию `default.target`.

**Когда сервис оживает.** При первом входе в сессию pam_systemd
запускает user-менеджер, тот активирует `default.target` и поднимает
все юниты из `default.target.wants`. Linger не включается, поэтому до
первого входа демон не работает — для рабочего стола разницы нет.

**Проверка после установки** (в сессии установленной системы):

    systemctl --user is-enabled syncthing   # enabled
    systemctl --user status syncthing        # active (running)

**Где что лежит:**

- команда включения — `install/regen-custom-commands.py`, секция
  `syncthing`;
- пункт меню (запуск демона + открытие веб-панели) —
  `install/files/desktop/wdistr-syncthing.desktop`, доставляется тем же
  скриптом в `/usr/share/applications`;
- исходники настроек пользователя в целом — `install/files/`
  (fish-shell, PATH, SSH-ключ — доставляются там же, в `custom_commands`).

**Штатные возможности archinstall** (проверено по исходникам 4.5):
описание пользователя (`users`) содержит только `username`, `password`,
`sudo`, `groups` — для user-сервисов поля нет; поле `services` в конфиге
включает только системные юниты. Поэтому свои user-сервисы включаются
через `custom_commands`, как описано выше.

## Несколько и будущие пользователи

Команда выше цепляет первого обычного пользователя (uid 1000–65534) —
этого достаточно для типовой установки с одним аккаунтом. Дальше три
случая:

1. **Пользователь уже добавлен вручную.** Та же команда симлинка, но
   вместо динамического `$U` подставляется его имя; выполняется от root
   в целевой системе.

2. **Нескольких пользователей создаёт архинсталл при установке** —
   штатный механизм профилей. Любой профиль реализует метод
   `provision(install_session, users)`, который пишет файлы в домашний
   каталог каждого пользователя из конфига установки (пример из
   archinstall 4.5: niri-профиль создаёт drop-in
   `~/.config/systemd/user/niri.service.d/dms.conf`). Работает только
   при установке — пользователей, добавленных после, профиль не видит.
   Наш профиль сейчас пуст (`profile_config.profile = {}`).

3. **Новые пользователи, добавляемые после установки** — `/etc/skel`:
   шаблон домашнего каталога, который `useradd -m` целиком копирует в
   home создаваемого пользователя. Симлинк сервиса, лежащий в
   `/etc/skel/.config/systemd/user/default.target.wants/`, получит
   каждый новый обычный пользователь; системные учётки обычно создаются
   без каталога и останутся без сервиса. Пока не реализовано — способ
   записан, ввести при появлении второго пользователя.
