## Зачем

7.2.15 — последнее ядро ветки 7.2 (отмечено EOL). Пользователь хочет оставить его резервным на случай проблем в 7.3. Пакетов «с нумерацией» в Arch нет — версия `linux` в репозитории одна, при обновлении на 7.3 pacman удалит файлы 7.2.15. Поэтому ядро заморожено руками.

## Что где лежит (снято 2026-11-11 с работающей системы)

`~/kernel-pin/` (принадлежит пользователю, переживает `pacman -Scc` и обновления):

| Каталог | Содержимое | Назначение |
|---|---|---|
| `boot/` | `vmlinuz-linux` (17 МиБ), `initramfs-linux.img` (46 МиБ) | образ ядра и initramfs; fallback-файла нет — в `linux.preset` только пресет `default` |
| `modules/7.2.15-arch1-1/` | 528 МиБ | полный каталог модулей; имя с версией сохранено обязательно |
| `pkg/` | `linux-7.2.15…pkg.tar.zst` + `linux-headers-…` + подписи | архивный источник, если копии повредятся |

Пакеты взяты из `/var/cache/pacman/pkg` до воскресной очистки `sys-update` (скрипт после успеха гоняет `pacman -Scc`).

## Права

Файлы в `boot/` сняты с правами `600` (такими они были в `/boot`), и при раскладке на ESP выглядят так же. Править права не нужно и не получится: `/boot` — vfat с `fmask=0177,dmask=0077` (строка в `/etc/fstab`), режим файлов задаётся опциями монтирования, `chmod` на vfat не работает. GRUB читает раздел собственным драйвером vfat, минуя права Linux. Прежняя редакция требовала выставить `644` — это ошибка от мысленного ext4 (уточнено 2026-11-15).

## Раскатка на 7.3 (выполнено 2026-11-15)

Порядок, в котором это сделано на рабочей машине после обновления до `7.3.4-arch1-2`. pacman удалил файлы пакета `linux` вместе с `/usr/lib/modules/7.2.15-arch1-1` — так и задумано.

1. Модули вернулись из заморозки:

   ```sh
   sudo cp -a ~/kernel-pin/modules/7.2.15-arch1-1 /usr/lib/modules/
   sudo chown -R root:root /usr/lib/modules/7.2.15-arch1-1
   sudo depmod 7.2.15-arch1-1
   ```

   Проверка: в `modules.dep` столько же записей, сколько файлов `.ko*` в дереве (6521 против 6521, снято после восстановления; файлов 528 МиБ), `modinfo -k 7.2.15-arch1-1 vboxdrv` отдаёт `updates/dkms/vboxdrv.ko.zst` версии 7.2.22, `modules.dep` связывает `vboxnetadp → vboxdrv`. Пустой вывод `modprobe -S 7.2.15-arch1-1 -n ext4` — норма: `ext4` собран в само ядро (`modules.builtin`); пустой вывод для `vboxdrv` — модуль уже загружен в работающем ядре. Путь версионированный, пакету не принадлежит (pacman о нём не знает), с каталогом 7.3 не конфликтует.

2. Файлы загрузки лежат на ESP в `/boot/reserve/`, без переименований под `-7215`:

   ```sh
   sudo mkdir -p /boot/reserve
   sudo cp ~/kernel-pin/boot/vmlinuz-linux /boot/reserve/vmlinuz
   sudo cp ~/kernel-pin/boot/initramfs-linux.img /boot/reserve/initramfs.img
   ```

   Сверка: `sha256sum` даёт `3133feb3…` (vmlinuz) и `a6aaaf5c…` (initramfs) — те же, что в `~/kernel-pin/boot/`. Внутри initramfs — модули `7.2.15-arch1-1` и запаянный микрокод AMD (`lsinitcpio -a`), поэтому отдельный `/amd-ucode.img` в записи дублирует микрокод, но вреда не даёт.

3. Запись в `/etc/grub.d/40_custom`, затем `sudo grub-mkconfig -o /boot/grub/grub.cfg`:

   ```
   menuentry 'Arch Linux (резерв, ядро 7.2.15)' {
       search --no-floppy --fs-uuid --set=root 9F04-1CED
       linux /reserve/vmlinuz root=UUID=633bdba1-0093-49b3-98dd-8116c0f18638 rw rootfstype=btrfs rootflags=subvol=@ loglevel=3 quiet
       initrd /amd-ucode.img /reserve/initramfs.img
   }
   ```

   `rootflags=subvol=@` нужен по образцу сгенерированных записей: `/etc/grub.d/10_linux` (строки 70–73) вычисляет подтомень из пути системы и подставляет параметр всем своим записям. Без него ядро монтирует корневой уровень btrfs и не находит `init`. Если `@` когда-нибудь назначат подтомем по умолчанию, параметр останется безвредным (тот же подтомень, но по имени). Опыт 2026-11-15: в первой редакции записи параметра не было, добавлен точечным `sed` по строке `linux`.

4. Заголовки (`linux-headers-7.2.15`) для загрузки не требуются, они нужны компиляции модулей под резервное ядро — на всякий случай в заморозке есть и распакованное дерево `modules/7.2.15-arch1-1/build`.

## Не проверено

Реальная загрузка резервной записи не выполнялась (состояние на 2026-11-15): модули, файлы на ESP и `grub.cfg` на месте, но пункт «резерв» в меню GRUB ещё не выбирался. Проверка после перезагрузки:

```sh
uname -r                             # ожидаем 7.2.15-arch1-1
lsmod | grep vboxdrv                 # модуль из восстановленного дерева
sudo btrfs subvolume get-default /   # заодно ответит, был ли rootflags обязателен
```

## Опыт 2026-11-11: разъезд sync-баз и защита wdistr-sys-update

Эксперименты с зеркалами привели к несогласованным базам pacman: `core.db` старая (openssl 3.6.5), `extra.db` свежая (55 пакетов требуют `libcrypto.so=4-64`) — `pacman -Syu` падал с «неразрешимыми зависимостями». Лечится принудительным `-Syy` со свежего зеркала (koyanet уже отдавал согласованную пару openssl 4.1.0 + linux 7.2.15).

Бояться при этом нечего — комментарий в `install/files/sys-update.sh` (коммит 0b8d78d): вопрос pacman «skip these packages?» — `noyes()`, дефолт N; `--noconfirm` отвечает дефолтом → транзакция падает целиком (`ALPM_ERR_UNSATISFIED_DEPS`), частичного обновления нет, `rc!=0` в лог, кэш не чистится, `OnFailure` повторяет через 4 часа.

Примечание про timeshift: таймер `wdistr-timeshift-check` щёлкает каждый час, `--check` создаёт снимок только по расписанию (daily/weekly) — «непосредственно перед обновлением» снимок не гарантируется. `Before=` в сервисе лишь расставляет очередь при одновременном старте.
